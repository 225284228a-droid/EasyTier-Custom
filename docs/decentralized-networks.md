# 网络管理：去中心识别 + 核心设置统一下发

## 模型

网络页不区分“中心托管”和“去中心批量”两种模式，只有一种网络：

- **网络 = 设备上同一网络名的实例。** `frontend/src/modules/networkDiscovery.ts` 扫描在线
  设备的运行和已停止实例，按 `network_name` 分组；分组键 `name:<网络名>` 与拓扑地球仪
  的节点身份相同，所以网络页和地球仪看到的是同一组节点。中心模式下还会合并控制台记住的
  实例（`GET /api/v1/mesh/members`），离线成员、待补发和临时节点因此也能显示。
- **控制台只统一管理“不一致就失联”的核心设置**：网络名、网络密码、安全模式开关、关闭
  加密、加密算法。依据：握手校验网络名和密码摘要（`peer_conn.rs`），安全模式决定握手方式；
  非安全模式下加密器按实例由密码派生（`peer_manager.rs`），不加密的一端会拒收加密包
  （`tunnel/encrypt/mod.rs`）。压缩靠每个包的标记、流量伪装两端协商，不一致不会失联。
- **三个名字各管各的**：
  - **网络名称**（`network_name`）是组网身份，与密码一起决定节点能否互联；网络页按它识别网络。
  - **网络密码**（`network_secret`）参与握手校验，不一致就失联。
  - **网络显示名称**只用于显示：写入每个成员配置的 `instance_name`（`api_manage.proto` 字段
    50086，能力 `config:instance-name-v1`），设备上显示配置时用它覆盖原来显示的名称；留空则显示
    网络名称。它不影响组网，但和核心设置一起下发、一起补发。官方内核总是用网络名称命名实例，
    不保存单独的显示名称，所以显示名称不会写给官方节点。
- **其他字段控制台都不管**，包括初始节点、监听、虚拟 IP、主机名、子网代理。网络页的批量
  修改器仍可编辑它们，但只写入当前在线并选中的成员，没有补发。
- **ACL 已移除**：网络级 ACL 依赖成员登记表，每个成员的 ACL 又依赖全体成员，与“只补一次”
  冲突，多控制台还会互相覆盖。界面和接口都已去掉；设备文件里已有的 ACL 保持原样。

## 核心设置下发（`easytier-web/src/central_network/core_sync.rs`）

1. 每个对账周期（5 秒）读取在线、支持 revision 的设备的配置目录（会话缓存，节点宣告变更
   时才重新读取），记录每个实例的核心设置和时间戳（表 `mesh_observations`）。离线设备保留
   最后一次记录，所以离线成员仍能被找到。
2. 网络页修改核心设置时（`POST /api/v1/mesh/core`），控制台按网络名找出全部成员：
   - 在线成员：读取最新版本，只写与目标不同的核心字段，带 revision 写入，期间文件被别人
     改过则报冲突、不覆盖；
   - 离线成员：记一条补发记录（表 `mesh_core_replays`），包括修改前的核心值和时间戳、这次
     的改动和时间戳。同一成员多次错过修改时合并成一条，按字段以后者为准。
3. 成员重新上线后的第一个对账周期补发一次，**无论是否发出记录都删除**。只有下面任一情况
   才发：
   - 节点的核心值仍是修改前的值，且时间戳不新于当时（期间没人动过）；
   - 节点时间戳新于当时但旧于这次修改（期间只被别的控制台写过，手工修改不改时间戳）。
   补发时使用这个控制台能看到的同网络最新值（在线成员里时间戳更新的那份优先）。
4. 之后本地再改，控制台不会改回。

官方节点（以及不带配置目录运行的内核）没有自己的配置目录，配置由控制台保存，节点在线时由
控制台下发。对这类成员直接**强制覆盖**控制台保存的那份配置的核心设置，保持原来的启停状态，
在线的立即生效，离线的在重新连上时由控制台下发。官方节点只能连一个控制台，不存在竞争，所以
不需要时间戳和“修改前的值”比较。外部 Console（webhook）模式没有中心服务，所有字段都在
浏览器里写在线成员。

## 多控制台

一个内核可以同时连多个控制台（`--config-server` 逗号分隔，`easytier/src/core.rs`），这些
连接共用同一个实例管理器和配置目录，所以各控制台读到的是同一份文件和版本。

- **识别自动一致**：网络来自设备文件，A 改过的值 B 下一个周期就能看到。
- **先后顺序**：设备配置新增字段 `network_sync_at`（`api_manage.proto` 字段 50085，TOML 顶层
  键，能力 `config:network-sync-v1`），记录最后一次核心设置修改的 **UTC Unix 毫秒**。它是绝对
  时刻，与控制台所在时区无关；为防止机器时钟偏差，新时间戳取“当前 UTC 毫秒”和“已见最大
  时间戳 + 1”中较大者。内核运行时不使用它，官方内核会过滤这个字段，此时只做“修改前的值”
  比较，不排先后。
- 一个时间戳足够：补发记录自带修改前的值，能识别手工修改；时间戳只负责区分“另一个控制台
  写过”以及谁更新。

## 中心网络与临时节点

中心网络记录保留，用于临时节点、凭证和接入点：

- 只能添加**临时成员**；永久成员由设备自己的配置组网，通过识别出现在网络页。迁移
  `m20261102_000014_mesh_core_sync` 先删除永久成员的下发记录再删除成员，设备上的实例保留
  （若只删成员，下发记录会把它们当成删除）。官方节点上的配置作为控制台保存的普通配置保留。
- 临时节点的配置仍由控制台整份覆盖下发；网络名、安全模式和加密设置跟随中心网络记录。
- 中心网络记录与核心设置双向跟随：在网络设置里修改名称、密码、安全模式会下发给全部成员；
  在网络页修改同名网络的核心设置也会更新记录，临时节点和接入点随之更新。
- 临时节点凭证要由持有网络密码的节点广播才被全网信任（`peer_ospf_route.rs`）。接入点实例
  本身带有凭证；此外控制台把凭证写入在线永久成员的 `managed_credentials`，只增删自己写过的
  那些（表 `mesh_credential_deliveries`），不会冲掉其他控制台的凭证。

## 验证

- `cargo test -p easytier-web`：`core_sync` 单元测试覆盖只写不同字段、保留节点密钥、合并多次
  修改、补发条件、UTC 时间戳排序和输入校验。
- `cargo test -p easytier-core --lib config::`：`network_sync_at` 的 TOML 往返。
- `cargo test -p easytier-proto`：字段编号清单。
- 前端：`pnpm --dir easytier-web/frontend test:unit`，`node scripts/test-network-config.mjs`。
